# Security audit and stress test (6 November 2026)

Scope: branch `main` at `7a0db1f` (version 0.7.51, not released yet). Three separate reviews, each by an agent that did
not write the code, each starting its own copies of the program with temporary folders and talking only to
`127.0.0.1`. Nothing was sent to the real meeting point, to AWS, or to GitHub.

1. **The launcher on the player's own computer** (local web server, every `api_*` call, the page, the problem-report
   scrubber): about 80,000 hostile HTTP requests across 125 methods, about 30,500 direct calls across 127 methods,
   6,000 mixed calls from 50 threads, and 8,000 idle connections. No crash, no hang, no write or delete outside the
   chosen folders, no response with a token, and no other player's address. The page was fed script and markup in every
   text field and ran none of it.
2. **The servers** (lobby, relay, meeting point, key agreement and tunnel): malformed and oversized protocol input,
   auth between rooms, 5,000 idle connections, 600 TLS handshakes at once, 10,000 complete room lifecycles (60,000
   requests in 17.7 seconds, no errors, memory flat), `kill -9` in the middle of saving eight times. 33 different calls
   were made from two marker addresses and every response, saved file, replay and log was searched for those
   addresses: no hit, also through a real meeting point.
3. **The friends service, updates, the release and what leaves the computer**: friends operations and the moderation
   console, the cryptography against reference implementations, the update signature code (RFC 8032 vectors and 2,400
   altered signatures), archive unpacking, the uninstall, the workflows, and every network call against its permission.
   All 235 commits and the working tree were searched for keys and tokens: none.

Each real finding was fixed with a test that fails without the fix. Results: see "Results" at the end.

## Fixed

### High

- **The match tunnel accepted a guest nobody had given a key to.** For an unknown identity the TLS-PSK callback returned
  a fixed all-zero stand-in key, so a client that used any identity and that key completed the handshake and read the
  host's stream. It now returns a fresh random key (`adapters/retroarch/tunnel.py`). Present since the tunnel was written; the
  relay and the room's membership were the only other gates.
- **A friends service could get the key of another conversation by tricking a report** (`launcher/friends.py`). A report
  sent the keys of the reported message and those before it, opened without checking which conversation or author they
  belonged to, so a service that slipped another conversation's message into the thread got that message's key back.
  Each envelope is now opened against its own conversation and author.

### Medium

- **Friend secrets were stored in plain text** in `players.json`; they are now stored as a SHA-256 hash (older files
  convert on first start), and the file is owner-only on Windows as well.
- **A flood of made-up reports pushed real open ones out** (the oldest 5,000 were kept). Handled reports go first now,
  then the oldest open reports of whoever has filed the most.
- **Uninstall with "keep my saves" followed a symlinked or junctioned `emulators` folder** and deleted what it pointed
  at; it also accepted any folder with an `emulators` subfolder as its own. Links are only unlinked, and that subfolder
  alone no longer counts.
- **Wrong guesses at invite codes and the access key were counted per IPv6 /64**, so whoever holds a /48 had 65,536
  separate budgets and could use up the global budget. Counted per /56 now.
- **A guest that paired at the meeting point and then said nothing kept the host's slot** for ten minutes. It must now
  start speaking within the 10-second window the host already had.
- **Connecting to a friend's server through a meeting point had no permission.** It now needs "Meeting point for
  friends outside my home" (version 3: asked again).
- **Problem-report scrubber** let through: `server_access_key=...`, `Authorization: Bearer ...`, "password is ...",
  IPv6 after a label or before a full stop, IPv4 glued to letters, friend codes, other computers' names, `Name#1234`
  tags, and names hidden with invisible characters. All scrubbed now.
- **Per-address limits did nothing behind a reverse proxy on the same computer** (every request looks like loopback).
  `--trusted-proxy` counts the last `X-Forwarded-For` address.

### Low

- The launcher's page server now refuses a request with another site's `Origin` even with the token, reads the media
  type exactly, answers a body nested hundreds of thousands deep with a 400 (it printed a traceback and dropped the
  connection), and sends `Referrer-Policy: no-referrer` and `Cross-Origin-Resource-Policy: same-origin`.
- A text such as "false" counted as a yes for `confirm`, `delete_saves`, `permanent`, `delete_created` (and as "no" for
  the keep and remove-program defaults). Only a real `true` is a yes now.
- The friends service accepted public keys that make every shared secret the same (a friend could break messages
  for the whole group); they are refused, and a bad key in a chat says so instead of crashing the app.
- A TOTP code written with non-ASCII digits gave a different error from a wrong one, and was not counted.
- An update file is hashed again right before it is unpacked, and a 7-Zip package that unpacks to more than 4 GiB is
  refused before anything is written.

## Still open

1. **`install.ps1` (and `lp.ps1 install`) check only the SHA-256 and Authenticode, not the Ed25519 signature.** The
   signature protects the in-app updater. A new install made with `irm ... | iex` trusts whoever can publish a release.
   Fixing it needs an Ed25519 check in PowerShell (about 60 lines of `System.Numerics.BigInteger`); it was left because
   it can not be run or tested without Windows, and a mistake would stop every new install. Do it with a Windows
   machine at hand, and keep it failing closed.
2. **The update signing key is a repository secret** any workflow on any branch can read. Move it into a protected
   GitHub Environment and protect `main` and `v*` tags (steps in `docs/RELEASE.md`). This is a setting in GitHub, not code.
3. **RetroArch listens on every network interface** (it has no bind option), so a device on the same home network
   can connect straight to the host's RetroArch on its fixed port and skip room approval and the relay. Not reachable from
   the internet (nothing opens a port). Not tested here (no RetroArch). Options: a random port per match with a firewall
   rule that blocks other computers, or a RetroArch that offers a bind option.
4. **The launcher page's session cookie is not scoped to its port**, so another web service on `127.0.0.1` that the
   player's own browser visits is sent it and could replay it to read the API token. The app's own window uses a
   private browser profile; `--no-browser` and a default browser are exposed. The fix (keep the token in the page, not in a
   cookie-gated page) changes how the page loads and needs its own change.
5. **Home-network server codes hold the host's home-network address.** `docs/canonical/SPEC.md` ("Addresses", 1)
   allows exactly this (RFC 1918 addresses, no meeting point), and so does the code; `IDENTITY.md` principle 2 says
   "hold no address". The two canonical files disagree. A wording proposal is in
   `docs/proposals/2026-11-06-identity-wording-home-network-codes.md`.
6. **Smaller:**
   - The emulator path accepts any existing file and per-game launch options become its arguments (like Steam launch
     options). Anyone with the API token can therefore run programs as the player.
   - A 66 MB DAT file takes 5.7 s and 1.1 GB of memory to read (the limit is 128 MB).
   - The invite and access-key budgets are global per server: one holder of the key can use up the per-minute budget.
   - Replay recording is capped per room but not across all rooms, and writing a big snapshot pauses the server for a
     moment (a probe saw 434 ms).
   - A 3 MB request with no line ending over TLS resets the connection instead of answering with an error.
   - A friend's invisible-character name can look identical to another's.
   - Git-mode updates and `deploy/setup-vps.sh` do not check a signature.
   - The meeting point's TLS key is in the instance's start-up script (open item from 2026-11-04); not checked.

## Checked and sound

- Every `api_*` call under hostile input: 0 server errors, 0 hangs over 5 s, valid `user_data.json` and a clean restart
  afterwards.
- Host header, one-time key, cookie flags, token, methods, content type, paths, request smuggling, oversized and slow
  requests; the page's CSP held against injected markup in every text field.
- Between rooms: 13 host-only operations refused to a guest, no credential works in another room.
- Resource limits held under 5,000 idle connections and 600 simultaneous handshakes; crash during a save never left a
  half-written file; corrupt state files were set aside and the server started.
- **Addresses:** none in any server response, event, saved file, replay or log, with and without a meeting point.
- Cryptography matched the reference implementations (X25519, ChaCha20-Poly1305, HKDF, TOTP, Ed25519); all 18
  low-order points refused; no way found for a lobby to force the old shared-key tunnel.
- Every network call checked is behind its permission, and the permission texts say the site sees the player's address.
- Actions in the workflows are pinned by commit, tag text reaches scripts only through `env:`, the build job has no
  secrets, installs use hashes.
